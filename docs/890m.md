# strixite on the Radeon 890M (gfx1150, 96 GB)

This fork retargets strixite from Strix Halo (gfx1151, 128 GB) to the **Radeon 890M** iGPU (Strix Point, gfx1150) in a
machine with **96 GB of unified memory**. Everything else - the model, the weights file, the server, the OpenAI API -
is upstream's, unchanged.

> [!IMPORTANT]
> **Untested on hardware.** The changes were made and checked without a gfx1150 machine or ROCm: the host-only code
> has a test (`check_sysmem`), and the edited server compiled against a stub HIP header. The kernels were not rebuilt
> or run. The memory figures below are estimates derived from upstream's published numbers. The server's startup log
> prints the real ones, and refuses to start rather than overcommit (see [Checking](#checking-your-numbers)).

## What changed, and why

| change | why |
|---|---|
| `STRIX_GPU_ARCH` defaults to `gfx1150`; presets `890m`, `890m-debug`, `890m-roctx` | the device code is built for the 890M. The upstream presets `strix*` remain and build gfx1151 |
| `STRIX_HOST_ARCH` (default `znver5`, falls back to `znver3`) | Strix Point's CPU cores are Zen 5; upstream's host flags were `znver3` |
| defaults `capacity 131072`, `chunk 4096`, `ngram-cache-rows 2097152` | upstream's 512k / 16384 / 8M rows need 95.3 GiB of GPU buffers plus 3 GiB of row cache: more than a 96 GB machine has |
| startup log line + warning if the binary's arch differs from the device | a gfx1151 binary on this machine would fail with `invalid device function` at the first kernel |
| **GTT preflight** (`gtt-check = on`, exit status 5) | the default GTT limit is typically about half of RAM (~46 GiB here); the weights are 65.9 GiB. Without it the failure is a `hipMalloc` error mid-load. With it, the server says which kernel parameters to set |
| container files for gfx1150 | the TheRock tarball and build preset |

The kernels are untouched. They were already generic gfx11 wave32 / WMMA code, and the heuristics that depend on the
GPU's size read it from the device: attention's key splits (`4 x` multiprocessors), the 128- vs 64-row WMMA tile
(`>= 8` blocks per WGP), and the cooperative top-k's resident workgroups. HIP should report the 890M as 8 WGPs (16 CUs)
where Strix Halo has 20 (40 CUs), and all of those scale down with it.

### What is not retuned (and would be the next step)

The constants upstream measured on gfx1151 stay as they were, because they can only be set by measuring:

- QSA top-k path thresholds (`kQsaTopkRowMaxBlocks = 16384`, `kQsaTopkCoopMaxBlocksT1 = 40960` in `kernels/qsa.hpp`) -
  with 8 WGPs instead of 20 the row / cooperative crossover probably moves;
- the split-K rule of the GEMV kernels (`split_k` in `kernels/linear.hip` and its Q4 / Q5 / Q6 / Q8 siblings);
- `mtp-draft = 7` and `mtp-margin = 2`, tuned on Strix Halo's balance of compute and bandwidth; sweep 3 / 5 / 7 here.

Decode streams the active weights from memory every step, so it is bound by memory bandwidth. The 890M has a 128-bit
memory bus: ~90-120 GB/s depending on whether the machine has DDR5 SO-DIMMs or LPDDR5X and at what speed - against
Strix Halo's ~256 GB/s. So expect something like 35-50% of upstream's ~47-50 tokens/s, not that figure. That is an
expectation from the bandwidth ratio, not a measurement.

## Setup

**1. BIOS.** Set the iGPU's dedicated memory (UMA frame buffer) to the **minimum** (512 MB or "Auto"). A large
carve-out is subtracted from what Linux sees, and the GPU here allocates from system RAM anyway.

**2. Kernel parameters** - give the GPU 88 GiB of the machine's ~93 GiB (the server also prints the values for your
exact `MemTotal` if the limit is too low):

```
amdgpu.gttsize=90112 ttm.pages_limit=23068672 amd_iommu=off
```

Add them to the bootloader's command line and reboot. `cat /sys/class/drm/card*/device/mem_info_gtt_total` should
report ~94,489,280,512 bytes. (A machine with another GPU - an NVIDIA card has no such file - works: the server reads
the largest AMD value.)

**3. Toolchain.** TheRock's ROCm for gfx1150: tarballs are named `therock-dist-linux-gfx1150-<VERSION>.tar.gz`
(from AMD's nightly tarball index, `rocm.nightlies.amd.com/tarball/`). Upstream was tested with ROCm `10.1.0a20260822`,
and builds of that same version exist for gfx1150 (lemonade's llama.cpp builds list it), so start there. Check that the
file exists for gfx1150; if it doesn't, take the nearest. Extract it to `~/tools/therock-tarball/install`, or set
`STRIX_ROCM_ROOT`.

**4. Build.**

```sh
cmake --preset 890m && cmake --build --preset 890m
build/890m/check_sysmem            # host-only test of the preflight; "all cases pass"
```

**5. Weights** - the same files as upstream (`wemoh/Qwen3.8-Flash-Next-strixw`, ~115 GiB on disk: 65.9 GiB of weights
that go to the GPU, 48.3 GiB of n-gram table that stays on the SSD). Nothing to re-convert.

**6. Run.**

```sh
build/890m/strix_server --config deploy/strix-server.conf
```

## The memory arithmetic (96 GB)

Upstream's figures (`docs/memory.md`): GPU buffers 95.3 GiB at `capacity 524288`, `chunk 16384`, of which the weights are
65.9 GiB and the KV cache + state ~13.4 GiB (halving the capacity frees 6.7 GiB, so ~27 KiB a position). The rest,
~16 GiB, is work buffers that scale with `chunk` (at most ~1 MiB per chunk token). The n-gram row cache is ~384 B a row.

Machine: 96 GiB of RAM, ~93 GiB visible as `MemTotal` after firmware reserves (check yours); ~2 GiB for the OS and services.

| `capacity` | `chunk` | `ngram-cache-rows` | GPU buffers | MemAvailable after load | startup check needs | left for the RAM prompt cache |
|---|---|---|---|---|---|---|
| **131072 (default)** | 4096 | 2097152 | ~73.3 | ~17 | 4 + 3.5 = 7.5 | ~9 |
| 131072 | 8192 | 2097152 | ~77.3 | ~13 | 7.5 | ~5 |
| 196608 | 4096 | 262144 | ~75 | ~16 | 4 + 5.2 = 9.2 | ~7 |
| 262144 | 4096 | 262144 | ~76.6 | ~14 | 4 + 6.8 = 10.8 | ~3.5 |
| 524288, `prompt-cache-gib = 0` | 4096 | 262144 | ~83.3 | ~7.5 | floor 4 | - (no prompt cache) |
| upstream's 524288 / 16384 | | 8388608 | 95.3 | below zero | - | does not fit |

All in GiB; estimates. With a prompt cache the check is `MemAvailable >= margin + one saved state at full capacity`
(`docs/memory.md`); with none it is the 4 GiB floor. A 512k context without a prompt cache means re-reading a
conversation whenever it is switched away from - that is what the prompt cache is for.

The 88 GiB GTT limit is also a safety bound: GPU allocations can never take more than 88 of the ~93 GiB, so the
machine keeps at least ~5 GiB, well above the ~0.5 GiB at which upstream saw hard hangs.

### Recipes

Edit `deploy/strix-server.conf`, or pass the flags.

```
# longer context (256k)
capacity = 262144
ngram-cache-rows = 262144
```

```
# the desktop is also in use on this machine
prompt-cache-ram-margin-gib = 8
capacity = 65536
```

```
# not sure: start whatever fits, with each concession logged
low-memory = adapt
```

## Checking your numbers

At startup the log has, in order:

```
startup: GPU AMD Radeon 890M Graphics (gfx1150...), 8 multiprocessors (WGPs); binary built for gfx1150; GTT limit 88.0 GiB; MemTotal 93.x GiB
startup: GPU memory N GiB in K buffer kinds; ...
startup: memory: MemAvailable X GiB after loading (...); needs ...
```

- `GTT limit` below ~68 GiB: the server exits with status 5 and the parameters to set.
- `binary built for` differs from the device's arch: rebuild with `-DSTRIX_GPU_ARCH=<arch>` (`strix_server` warns).
- `MemAvailable` short of the check: exit status 4 and the settings that fit (`docs/memory.md`, "The startup check").

If the real "GPU memory" figure is higher than the table's, lower `chunk` first (2048 saves ~2 GiB more), then
`capacity`.

## Measuring

The server logs each request's `prefill` and `generate` rates (`serve/log.hpp`). To compare settings, send the same
prompt to each configuration and compare those two rows. Things worth sweeping on this chip: `chunk` 2048 / 4096 / 8192,
`mtp-draft` 3 / 5 / 7, `capacity`. Every "measured" number elsewhere in these docs is upstream's, on Strix Halo.

# Radeon 890M (`gfx1150`), 96 GB unified RAM

This is a **porting profile** of strixite's Qwen3.8-Flash-Next inference engine. It is not yet a benchmark-verified 890M release. The original upstream targets Radeon 8060S (`gfx1151`), Strix Halo and 128 GB; its speed and 512k-context claims **do not apply** to the 890M.

## Architecture and toolchain

The 890M is RDNA 3.5 (`gfx1150`) and supports the same wave32 WMMA instructions used by the gfx1151 kernels. This fork compiles all `.hip` sources with `--offload-arch=gfx1150`. No kernel occupancy, bandwidth or correctness measurements have been made on an actual 890M here. **TheRock provides a `therock-dist-linux-gfx1150-*` toolchain**; use a *Linux* package containing its HIP headers, compiler, amdhip64 runtime and gfx1150 device libraries (not the upstream project's gfx1151-only tarball). Starting sources:

- https://rocm.nightlies.amd.com/tarball-multi-arch/
- https://github.com/ROCm/TheRock/blob/main/SUPPORTED_GPUS.md

Host requires Linux with an appropriate AMDGPU/KFD driver, permission to access `/dev/kfd` and `/dev/dri/renderD*`, CMake >= 3.28, Ninja and a compatible GCC C++ standard library. The included CMake preset assumes ROCm was extracted to `$STRIX_ROCM_ROOT`, or `~/tools/therock-tarball/install` by default:

```bash
export STRIX_ROCM_ROOT="$HOME/tools/therock-tarball/install"
cmake --preset 890m
cmake --build --preset 890m -j "$(nproc)"
```

Do not reuse a build folder configured for `gfx1151`; ROCm clang and the chosen offload target must match. `cmake --preset strix` continues to build the original `gfx1151` profile if the ROCm installation supports it.

To confirm that HIP sees the Radeon 890M, run the toolchain's `rocminfo` (if included) and look for `gfx1150`. The server itself checks the selected GPU architecture **before** loading weights, and tells you if a different Radeon was selected. With multiple AMD GPUs set `ROCR_VISIBLE_DEVICES` or `HIP_VISIBLE_DEVICES` to pick the 890M (check local numbering). An NVIDIA RTX 2070 is not a HIP AMD execution target.

## 96 GB profile: memory constraints

**96 GB (decimal) is about 89.4 GiB.** A machine sold as 96 GiB has slightly more. Both are much less than the original upstream 128 GB. The upstream measured ~95.3 GiB GPU allocations at 512k context and 16k prefill chunks. This is more than your available physical RAM by itself, regardless of fast swap.

Configuration `deploy/890m-96gb.conf` (also the default no-config profile):

| option | 890M initial profile | original Halo | reason |
|---|---:|---:|---|
| `capacity` | **65,536** | 524,288 | smaller GPU KV/state allocation |
| `chunk` | **2,048** | 16,384 | smaller GPU prefill work buffers |
| `rope-yarn-factor` | **1** | 2 | use the trained RoPE range for 65k |
| `ngram-cache-rows` | **262,144** | 8,388,608 | ~0.1 vs ~3 GiB CPU row cache |
| `prompt-cache-ram-margin-gib` | **6** | 4 | margin for Linux, GPU allocations, desktop |
| `low-memory` | **fail** | fail | do not run when RAM safety check fails |
| `prompt-cache-gib` | **128** | 128 | maximum disk cache use; not preallocated |

**These are conservative initial settings, not a promise that startup succeeds.** The weights still require ~66 GiB of GPU-visible memory, plus activations, KV cache, workspaces and driver/OS overhead. 890M chip support, AMDGPU GTT aperture and resident memory must all be adequate. The runtime prints the actual GPU buffer tally and post-load `MemAvailable` when it succeeds. If it fails while allocating buffers, lower `--chunk` first (`1024` or `512`), then `--capacity` (`32768` or `16384`), and optionally disable MTP (`--mtp off`). The server's `low-memory` setting manages *host caches after GPU allocation*; it cannot recover from `hipMalloc` failure.

### Unified-memory GTT configuration

On Linux, the AMDGPU driver may limit the iGPU GTT allocation aperture well below the installed RAM. Check these values on the 890M DRM device (where the vendor ID is `0x1002`; ignore the NVIDIA card):

```bash
python3 tools/check_890m_memory.py
cat /proc/meminfo | grep -E '^Mem(Total|Available):|^SwapTotal:'
```

If your GTT aperture is less than the required **GPU-resident** allocations, change the AMDGPU/TTM limits using the documentation for *your Linux kernel and driver*. For example, **80 GiB** corresponds to `amdgpu.gttsize=81920 ttm.pages_limit=20971520` on driver versions where those parameters are supported (`gttsize` in MiB, `pages_limit` in 4 KiB pages). **Do not blindly copy the upstream 128 GB setting** (`amdgpu.gttsize=126976`) on a 96 GB machine; that exceeds physical RAM. Ensure the actual GPU allocation total fits *below* the aperture **and** leaves sufficient `MemAvailable`. Do not disable the IOMMU as a generic requirement, especially on mixed AMD/NVIDIA configurations. Kernel flags can change between driver versions: verify what is effective after reboot.

## Your RTX 2070 as a fast swap/cache tier

If you already have software that uses your RTX 2070 as an extremely fast swap backing store, keep it enabled for **pageable CPU memory and disk-backed prompt caches**. Swapping CPU memory to that device may help reduce SSD traffic. However:

- The ~66 GiB `weights.strixw` allocation is an AMD HIP `hipMalloc` buffer on the 890M and **not automatically eligible for Linux swap**.
- AMD's page-locked staging buffers (`hipHostMalloc`) are not pageable; neither are active AMD GTT GPU buffers generally a pool that can be backed transparently by NVIDIA VRAM.
- ROCm on the 890M cannot directly access RTX 2070 VRAM as extra unified RAM just because an external cache or swap solution exists. Supporting this would require explicit data movement and new kernels/memory management, and is **not** implemented by this fork.
- The model's int8 n-gram table (~48 GiB) is intentionally **disk-backed**, not loaded in full; only configured rows are cached in RAM. The prompt cache is disk-backed too. These can benefit from a fast underlying storage/page-cache hierarchy.

You can raise disk cache budget or RAM row cache **after** verifying the initial model fits. `--low-memory adapt` is an optional degraded-cache mode, *not* a replacement for physical memory.

## Launch

The server expects the same published model-format files, tokenizer and n-gram table as upstream (~115 GiB of model files on disk). Download them as described in [upstream weights instructions](../UPSTREAM-README.md) or `docs/tools.md`, or reuse your existing converted files. The n-gram table remains separate on disk.

```bash
export STRIX_MODELS_DIR="$HOME/models/strix-infer"
export HSA_DISABLE_COREDUMP_ON_EXCEPTION=1
build/890m/strix_server --config deploy/890m-96gb.conf
```

First inspect settings without touching the GPU:

```bash
build/890m/strix_server --config deploy/890m-96gb.conf --print-config
```

Lower-resource fallback (keeps disk caching):

```bash
build/890m/strix_server --config deploy/890m-96gb.conf \
  --capacity 32768 --chunk 1024 --mtp off
```

If you have room after GPU allocations have succeeded, increase capacity in steps, e.g. 65k to 96k or 131k (keeping `capacity <= 262144 * rope-yarn-factor`); monitor memory **after loading** and through a real prefill/decode session. The 890M has fewer compute units and less available memory bandwidth than Strix Halo, so expect different throughput and optimal kernel chunk sizes.

## Validation checklist

1. `cmake --list-presets` contains `890m`; all 890M `.hip` commands include `--offload-arch=gfx1150`.
2. `python3 tools/check_890m_memory.py` reports sufficient physical RAM and AMD GTT aperture.
3. `build/890m/strix_server --print-config` shows the smaller defaults; `--config deploy/890m-96gb.conf` agrees.
4. Start with `--capacity 32768 --chunk 1024` if you want the lowest-risk initial GPU allocation.
5. Verify `startup: Radeon device ... gfx1150`, `startup: GPU memory ...`, post-load `MemAvailable`, model output and GPU stability.
6. Benchmark short/long prompts and MTP-on vs MTP-off; **upstream speed and correctness benchmarks are only from gfx1151**.

### Optional container build

The fork's `deploy/container/Containerfile` and `build-image.sh` now select `gfx1150`, package `890m-96gb.conf`, and carry the matched ROCm userspace libraries. The build script intentionally requires a Git clone plus a separately downloaded and SHA256-verified `therock-dist-linux-gfx1150-*` tarball. Since this downloadable source archive has no `.git` directory, create a repository in it first if you want to use this reproducible image-build script:

```bash
git init && git add . && git -c user.name=Local -c user.email=local@example.invalid commit -m 'gfx1150 port'
deploy/container/build-image.sh . HEAD /absolute/path/to/therock-dist-linux-gfx1150-VERSION.tar.gz
```

The tarball must have a neighboring `.sha256` file. The container inherits the host's AMD GTT limits; passing `/dev/kfd` and `/dev/dri` does not solve physical-memory constraints. The original published Strix Halo image is **not** a 890M release.

The repo contains a host-only config smoke test at `tests/check_890m.sh`, which does **not** substitute for GPU correctness or performance validation.
